# ADR-0019: nic Distribution and Packaging

## Status

Proposed (2026-09-23)

Records how `nic` reaches users as settled by the pixi/prefix.dev distribution epic [#552](https://github.com/nebari-dev/nebari-infrastructure-core/issues/552): a conda package on prefix.dev repackaged from the GitHub release archives ([#579](https://github.com/nebari-dev/nebari-infrastructure-core/issues/579)), per-provider starter workspaces on `quay.io/nebari` ([#560](https://github.com/nebari-dev/nebari-infrastructure-core/issues/560)), and the move from our own channel to prefix.dev's shared `github-releases` channel ([#620](https://github.com/nebari-dev/nebari-infrastructure-core/issues/620), implemented by [#671](https://github.com/nebari-dev/nebari-infrastructure-core/pull/671)). [ADR-0005](0005-nic-config-cli-surface.md) records only the part of this that bears on config bootstrap (as amended by [#653](https://github.com/nebari-dev/nebari-infrastructure-core/pull/653)), and defers the packaging concerns here. Where this ADR describes the repository after the move (the bridge deleted, one channel, starter publishing as its own retrying workflow), it describes #671's end state, so it should merge after #671 and #653.

## Date

2026-09-23

## Context

Before #552, `nic` was installable three ways: a source build (`make build`, Go 1.26+), the signed release archives, or the Homebrew cask on macOS. A fourth, a standalone `curl | sh` installer, is in review ([#539](https://github.com/nebari-dev/nebari-infrastructure-core/pull/539)). All of them install a binary. None of them lets a deployment pin the toolchain next to its `config.yaml`, so "which `nic` deployed this cluster, with which OpenTofu" had no durable answer outside the operator's memory.

A pixi workspace does answer it. `pixi.lock` pins the exact `nic` package, including its sha256. `nic` constrains OpenTofu to the window in [ADR-0016](0016-opentofu-runtime-version-policy.md), which the workspace also resolves and locks. The embedded `.terraform.lock.hcl` pins the providers. One lockfile therefore pins the whole infrastructure toolchain, and a Nebari upgrade becomes a reviewable diff:

```diff
-nebari-infrastructure-core = "==0.13.0"
+nebari-infrastructure-core = "==0.14.0"
```

Getting there took three attempts, and the order matters for why the decision reads the way it does:

1. **conda-forge.** The epic started as a staged-recipes submission ([#559](https://github.com/nebari-dev/nebari-infrastructure-core/issues/559)), with its prerequisites: a third-party license bundle ([#555](https://github.com/nebari-dev/nebari-infrastructure-core/issues/555)), a source-tarball build under rattler-build ([#557](https://github.com/nebari-dev/nebari-infrastructure-core/issues/557)), and the autotick bot wired to our releases ([#564](https://github.com/nebari-dev/nebari-infrastructure-core/issues/564)). It was dropped on 2026-08-10 in favour of prefix.dev, and all four were closed as not planned.
2. **Our own prefix.dev channel, `nebari-dev/nebari`.** prefix.dev's `github-releases` channel is generated by [octoconda](https://redirect.github.com/hunger/octoconda), which repackages published GitHub release binaries. Onboarding is one entry in its `config.toml`, but the PR adding us sat unmerged. Rather than wait, [#616](https://github.com/nebari-dev/nebari-infrastructure-core/pull/616) shipped a bridge: a hand-written recipe under `packaging/conda/` and a `publish-prefix-dev` job in `release.yml` that cosign-verified the release's `checksums.txt` before repackaging, then uploaded over OIDC trusted publishing. In practice the pipeline never ran: no stable release was cut while it existed, so the channel only ever held v0.14.0, uploaded by hand as a seed on 2026-08-28.
3. **The shared `github-releases` channel.** The octoconda entry merged on 2026-09-03. octoconda imports the ten most recent releases of a repository it onboards, so the shared channel now serves `nebari-infrastructure-core` from 0.4.0 to 0.14.0 (there was never a 0.7.0 release) on all six platforms the release builds (linux, macOS, Windows × x86_64/arm64). That is ten versions against the bridge's one.

With both channels serving the same release, the question [#620](https://github.com/nebari-dev/nebari-infrastructure-core/issues/620) asked to be answered explicitly rather than by whichever merged first is live: do we install from a channel we do not control?

## Decision Drivers

- A deployment must be expressible as a lock-pinned workspace: toolchain, config and deploy tasks travelling together, diffable and rollback-able by version.
- The binary a user installs through a package manager should be the same bytes we built, signed and attested, not a rebuild whose provenance has to be argued separately.
- Maintenance cost stays near zero. A recipe, feedstock, license bundle or build matrix is work that recurs on every release and every Go or dependency bump.
- No install path may regress. The archives, Homebrew and source builds keep working, and the package is an addition to them.
- Prereleases stay off every channel, and a starter must never lock against a release candidate.
- Whatever we depend on outside the repository must have a documented failure mode and a way back.

## Considered Options

1. conda-forge feedstock, built from source in conda-forge's CI
2. Our own prefix.dev channel (`nebari-dev/nebari`), repackaging release binaries with a recipe we maintain
3. prefix.dev's shared `github-releases` channel, repackaged by octoconda with no recipe on our side

## Decision Outcome

Chosen option: **Option 3**, the shared `github-releases` channel. It is the shape #552 picked prefix.dev for in the first place, it already carries the last ten releases, and it lets us delete the recipe and publish job instead of maintaining them. The loss in the trust chain is real but small, and is covered below.

The rest of the distribution follows from that choice:

- **Package name: `nebari-infrastructure-core`.** Decided on [#556](https://github.com/nebari-dev/nebari-infrastructure-core/issues/556) over `nic` and `nebari-nic`. It matches the repository, the Go module path and the release archive names, and it is unambiguous in a search. `nic` reads to most engineers as "network interface card". Users type the package name once, in a `pixi.toml`, and the binary name daily, so the mismatch costs less than it looks. The binary is still `nic`, and `docs/operations/packaging.md` says so next to the install command.
- **Repackaged, not rebuilt.** The package contains the release binary unchanged, so it reports the release version, commit and build date from `nic version`. Verified for 0.14.0 on linux-64: `bin/nic` in the octoconda package hashes to `86127987…`, the same as the binary inside `nebari-infrastructure-core_0.14.0_linux_x86_64.tar.gz`.
- **Stable releases only, which depends on prereleases being tagged `-rc.N`.** octoconda does not read GitHub's prerelease flag. It skips a tag whose name contains `rc`, `alpha`, `beta` or `prerelease`, and otherwise takes everything before the first `-` as the version. A `v0.15.0-pre.1` would be packaged as `0.15.0`; since octoconda never rebuilds a version it already carries, the real `v0.15.0` would never reach the channel, and the v0.15.0 starter would lock against the prerelease binary without any error. So the tag shape is the enforcement: `release.yml` rejects any tag that is not `vX.Y.Z` or `vX.Y.Z-rc.N` before the release starts. Starters are published for stable releases only. We record this as our policy rather than inherit it from the tool's default. If release candidates ever need a channel, the version has to be normalised (`0.14.0rc1` sorts before `0.14.0`), and that is a new decision.
- **Publication is asynchronous.** octoconda runs on a two-hourly cron, but its runs start late and vary in length, so a release becomes resolvable one to two hours after the tag in the typical case and close to three at worst. Nothing in this repository waits for it. The archives and Homebrew cask are available immediately.
- **Starter workspaces are OCI artifacts on `quay.io/nebari/starters/<provider>`**, tagged with the `nic` version they pin, under the same quay project as `quay.io/nebari/charts`. Each one bundles `pixi.toml`, `pixi.lock`, a placeholder `config.yaml` and a README. `cmd/starters` generates them from `examples/`, so the config cannot drift from what CI validates. `local` and `aws` ship today.
  - A registry, not a git repository, because a tagged artifact pairs each starter with the release it pins, `nebi import` restores the whole workspace, lockfile included, in one step, and rollback is importing the older tag. Two versions can be imported side by side to compare their configs. `nebi diff` compares only `pixi.toml` and `pixi.lock`, so it shows the toolchain change between versions, not the config change. A template repository gives neither version pairing nor a lockfile that matches the release.
  - Not a `nic config init --template` flag, for the reasons ADR-0005 records: the starter does what `init` would have done, and also pins the toolchain and ships the tasks.
  - The unedited starter cannot deploy. `config.yaml` carries `CHANGEME` placeholders that `nic validate` rejects ([docs/operations/config-placeholders.md](../operations/config-placeholders.md)), and the workspace's `deploy` task `depends-on` `validate`.
  - Because the starters pin `nic` as a conda dependency, `pixi lock` cannot run until octoconda has published the release. Starter publishing therefore runs in its own workflow, fired by the release and retried hourly until the channel carries the version. It builds from the release's own tag and publishes one provider at a time (see [docs/operations/packaging.md](../operations/packaging.md)). Allow up to about four hours from tag to starters.

### The trust chain

What each link proves, and what it does not:

| Link | Proves | Does not prove |
|---|---|---|
| `checksums.txt` signed keyless with cosign by `release.yml` on a tag, plus a GitHub build-provenance attestation over the archives | The archives are the ones our release workflow produced ([docs/operations/verifying-releases.md](../operations/verifying-releases.md)) | Anything about a copy made later |
| octoconda's generated recipe pins the source to the release asset's URL and GitHub-computed sha256 digest | Within one octoconda run, the package was built from the asset GitHub described when octoconda read it. It does not cover a later swap: octoconda never rebuilds a version it already carries, so an asset replaced afterwards is ignored rather than rejected | That the asset is ours: octoconda does not check our cosign signature or attestation |
| octoconda publishes with `rattler-build publish --generate-attestation` over its own OIDC identity | The package was built by octoconda's workflow | That we built it |
| The package's `info/about.json` records `upstream-sha256` and the release download URL | A user can check the package against our **signed** `checksums.txt`. For 0.14.0 linux-64, `upstream-sha256` is `2583d113…`, the signed entry for that archive | Nothing on its own, until someone makes that comparison |
| The starter's `pixi.lock` records the package sha256 | Every later `pixi install` of that starter gets the same package bytes, so a replaced package on the channel fails the install instead of being picked up silently | That the first lock resolved the right package |

The bridge's one extra link was cosign verification before repackaging, done in our own CI. Moving to the shared channel gives that up. What replaces it is weaker but checkable: the digest pin plus the recorded `upstream-sha256`. Anyone who needs our signature in the loop can install from the archives, which carry it end to end. Trusting the channel also means trusting the octoconda maintainer and prefix.dev not to change the recipe template or the build script in a way that alters the payload. We accept that for a CLI binary whose archives remain the authoritative, signed distribution.

### Consequences

**Good:**

- No recipe, feedstock, license bundle, build matrix or publish credentials in this repository. #671 deletes `packaging/conda/` and the `publish-prefix-dev` job, and the old trusted-publisher binding is revoked as a one-time cleanup.
- Every release from 0.4.0 onward resolves, on all six platforms, and new releases arrive without anything done by hand.
- A deployment is a lock-pinned workspace, and a Nebari upgrade is a diff of it.
- One channel once #671 lands, so the starters, install docs and packaging docs have a single answer to "where does `nic` come from".

**Bad:**

- The channel is a third-party dependency. octoconda is one person's project and the shared channel is described as experimental. If we are dropped from `config.toml`, or octoconda stops running, new releases stop appearing and nothing in this repository fails. Escalation is an issue on octoconda. The way back is Option 2: the bridge recipe and publish job are recoverable from git history, and the `nebari-dev/nebari` channel still exists.
- The v0.14.0 starters on quay were locked against `nebari-dev/nebari`, so that channel has to stay available for as long as those tags are supported.
- A new release is not installable through pixi for up to about three hours, starters trail it by up to about four, and starter publishing has to be a retrying workflow rather than a step ordered by `needs:`.
- `nebi publish` also moves `:latest`, so a starter can only be published automatically for a release newer than any already on quay. Backfilling an older one is a manual publish plus a re-tag of `:latest`.
- Stable-only rests on a tag-naming convention that `release.yml` enforces, not on anything octoconda checks.
- The authenticity check between our signature and the installed package is available but not automatic. It is a comparison the user makes, not a step the channel enforces.
- Windows is packaged but not covered by the starters, whose workspaces declare only linux and macOS platforms.

### Out of scope

- **Filled, org-specific configs** on any public registry. A filled `config.yaml` carries a domain, region, availability zones, project name and GitOps repository URL; only the placeholder starters are published.
- **Out-of-tree provider plugins** ([ADR-0004](0004-out-of-tree-provider-plugins.md)). Plugin binaries installed from a manifest at runtime would sit outside `pixi.lock`, so "one lockfile pins the whole toolchain" holds only for in-tree providers. How plugins are distributed, and whether they go through the same channel and lock, is for the plugin work to decide.

## Options Detail

### Option 1: conda-forge feedstock

Submit a recipe to staged-recipes and maintain a feedstock that builds `nic` from the source tarball with conda-forge's `go-nocgo` compiler, updated by the autotick bot.

**Pros:**

- The most widely trusted conda channel, and the default in most pixi and conda setups.
- Builds from source in neutral CI, independent of our release pipeline.

**Cons:**

- The most work of the three: a transitive license bundle kept current, a source build that has to match GoReleaser's ldflags so `nic version` is right, feedstock maintainers, and review cycles on every recipe change.
- The package is a rebuild, not our signed artifact, so its bytes differ from the release and its provenance is conda-forge's, not ours.
- conda-forge does not accept repackaged binaries without an exception, so there is no low-effort route onto it later either.

### Option 2: Our own prefix.dev channel

Keep the bridge permanently: our recipe repackages the release archives, our CI cosign-verifies `checksums.txt` before reading any digest, and uploads to `nebari-dev/nebari` over OIDC trusted publishing.

**Pros:**

- Our signature is checked before a package exists, in CI we control.
- Publication happens inside the release run, so a starter can lock in the same run with a `needs:` edge.
- No dependency on a third party beyond prefix.dev itself.

**Cons:**

- A recipe and publish job to maintain, and a trusted-publisher registration that lives outside the repository and fails silently when the workflow or environment is renamed.
- No backfill: releases cut before the job existed are not on the channel and never will be.
- The free tier's 3 GB public quota holds about 17 releases at roughly 175 MB each, so it needs the Open Source plan or pruning.

### Option 3: Shared `github-releases` channel (chosen)

Let octoconda repackage our published releases into prefix.dev's shared channel on its own schedule.

**Pros:**

- Nothing to maintain in this repository. Onboarding was one line upstream.
- The last ten releases are already published, on every platform the release builds.
- The package payload is our release binary, byte-identical, and records the upstream digest it was built from.

**Cons:**

- Our signature is not verified before packaging, see [The trust chain](#the-trust-chain).
- Publication is up to two hours behind the release and cannot be triggered from here.
- A single maintainer and an experimental channel sit on the install path.
